# Архитектура и техническое задание MVP: корпоративный таск-трекер

## 1. Цель проекта

Веб-система управления задачами внутри одной организации, позволяющая:

- создавать задачи и назначать ответственных сотрудников;
- делегировать задачи на нижестоящие уровни организационной структуры, создавать подзадачи;
- контролировать сроки исполнения и отслеживать просрочки;
- вести историю изменений задач и действий сотрудников;
- рассчитывать рейтинг исполнительской дисциплины на основе истории событий;
- работать с Kanban-доской и списком задач;
- разворачивать систему на тестовом и основном серверах без изменения исходного кода.

Обновление доски в MVP — по действию пользователя или периодическому опросу backend, без требования мгновенной синхронизации между всеми пользователями одновременно.

Основной принцип: модульный монолит и минимально необходимая инфраструктура на старте, с возможностью расширения без переписывания.

## 2. Технологический стек

| Компонент | Технология | Назначение |
|---|---|---|
| Backend | Python + FastAPI | REST API, бизнес-логика |
| Валидация | Pydantic | Проверка входных/выходных данных |
| ORM | SQLAlchemy | Работа с PostgreSQL |
| Миграции | Alembic | Версионирование схемы БД |
| База данных | PostgreSQL | Единственная БД на MVP |
| Планировщик | APScheduler (отдельный контейнер) | Проверка сроков, генерация уведомлений, пересчёт рейтинга |
| Frontend | React + TypeScript | Kanban, списки задач |
| Reverse proxy | Nginx | HTTPS, маршрутизация |
| Контейнеризация | Docker + Docker Compose | Запуск и перенос приложения |

На первом этапе не используются: ClickHouse, Redis/Celery, WebSocket/SSE, MinIO. Подключаются по мере реальной потребности (см. раздел 12).

## 3. Схема взаимодействия

```
Пользователь → Nginx (HTTPS) → Frontend (React) ⇄ REST API ⇄ FastAPI (модульный монолит)
                                                                      │
                                                                      ▼
                                                                PostgreSQL
                                                                      ▲
                                                                      │
                                                   APScheduler worker (сроки, уведомления, рейтинг)
```

## 5. Организационная структура и права доступа

Единая организация (не мульти-тенантная система). Подразделения образуют дерево.

**Таблица `departments`:** `id`, `name`, `parent_department_id` (self-reference), `manager_id` (FK на users).

**Роли пользователя:** `admin`, `manager`, `employee`. Роль определяет базовый уровень доступа; делегирование задач вниз по дереву подразделений дополнительно проверяется по позиции пользователя в иерархии, а не только по роли.

Все проверки прав — на backend. Frontend может скрывать элементы UI, но это не заменяет проверку.

Проверка доступа учитывает: подразделение пользователя, его роль, связь пользователя с задачей (постановщик/исполнитель/ответственный/вышестоящий руководитель), запрашиваемое действие.

## 6. Модель задачи

**Таблица `tasks`:**

| Поле | Назначение |
|---|---|
| id | Идентификатор |
| title, description | Название, описание |
| status | todo / in_progress / review / done / cancelled |
| priority | Приоритет |
| created_by_id | Постановщик |
| assignee_id | Текущий исполнитель |
| accountable_id | Ответственный за итоговый результат |
| parent_task_id | Родительская задача (подзадачи) |
| deadline | Срок исполнения |
| created_at, updated_at, completed_at | Временные метки |

Три разные роли не смешиваются: постановщик создал задачу; исполнитель выполняет; ответственный отвечает за итог. При делегировании меняется `assignee_id`; `accountable_id` автоматически не меняется.

**Переходы статусов** проверяются backend — нельзя отправить произвольный статус.

**Защита от циклов:** при назначении/изменении `parent_task_id` backend обходит цепочку родителей вверх; если целевой родитель уже встречается в цепочке (A → B → C: нельзя сделать A ребёнком C), операция отклоняется.

## 7. История событий (`task_events`)

Неизменяемый журнал: `id`, `task_id`, `actor_id`, `event_type`, `created_at`, `payload`.

Фиксируются: создание задачи, изменение статуса, смена исполнителя, изменение дедлайна (с переносами), **смена ответственного (`accountable_id`) — отдельным типом события**, завершение/отмена.

Изменение задачи и запись события в `task_events` выполняются в одной транзакции.

## 8. Сроки и рейтинг исполнительской дисциплины

**Контроль сроков:** хранятся дата создания, дата назначения исполнителю, установленный срок, фактическая дата завершения, история переносов срока. Все даты — в UTC, пользователю отображаются в локальном часовом поясе. Просрочка определяется по сроку и фактическому завершению, а не только по статусу.

**Рейтинг — часть MVP.** Рассчитывается непосредственно средствами PostgreSQL по истории `task_events`, отдельная аналитическая БД не требуется.

Базовые показатели: доля задач, выполненных в срок; доля просроченных задач; среднее отклонение от срока; количество завершённых задач.

Точная формула и веса показателей — согласовать с заказчиком до реализации Этапа 5 (см. раздел 11). До согласования Этап 5 реализует показатели как есть, без итогового взвешенного балла.

Пересчёт выполняется периодически планировщиком; рейтинг не должен незаметно изменяться задним числом.

## 9. Уведомления (только in-app в MVP)

Email, Telegram, push — не входят в MVP.

**Таблица `notifications`:** `id`, `user_id`, `task_id`, `type`, `message`, `created_at`, `is_read`, `dedupe_key`.

`dedupe_key` (например, `task_id + notification_type + deadline_version`) — уникальное ограничение в БД, предотвращает дубли при повторном запуске планировщика. При изменении дедлайна `deadline_version` увеличивается.

Если появится несколько экземпляров планировщика — потребуется распределённая блокировка или выделенный единственный worker.

## 10. Валидация и ошибки

Все входные данные — через Pydantic-схемы: обязательность полей, типы, форматы, длина строк, допустимые статусы/приоритеты, корректность дат, бизнес-ограничения, права доступа.

Единый формат ошибки:
```json
{"detail": {"code": "TASK_NOT_FOUND", "message": "Task not found"}}
```

Коды: 400 (бизнес-ограничение), 401 (не аутентифицирован), 403 (нет прав), 404 (не найдено), 422 (ошибка валидации), 500 (внутренняя ошибка).

## 12. Что сознательно отложено

| Технология | Когда подключать |
|---|---|
| ClickHouse | Когда объём событий и аналитика создадут реальную нагрузку на PostgreSQL. При подключении — transactional outbox: событие пишется в PostgreSQL в одной транзакции с изменением задачи, отдельный worker доставляет его в ClickHouse |
| Redis + Celery | Когда потребуются распределённые очереди и надёжные повторные попытки |
| WebSocket / SSE | Когда периодического обновления доски станет недостаточно |
| MinIO | Когда появится требование хранить вложения к задачам |

## 13. Docker и развёртывание

```
project/
├── backend/
├── frontend/
├── nginx/
├── docker-compose.yml
├── .env.example
├── .gitignore
└── README.md
```

Контейнеры: `nginx`, `backend`, `frontend`, `postgres`, `scheduler` (backend и scheduler — один образ, разные команды запуска).

Разные `.env` для dev/test/production; секреты не попадают в Git — только `.env.example`.

**Перенос между серверами:** те же версии Docker-образов (собранные один раз, протегированные), но конфигурация окружения отдельная через `.env`. Данные переносятся через `pg_dump`/`pg_restore`, изменения схемы — через Alembic. Это разные операции, не подменяют друг друга.

## 14. Production readiness (обязательно перед реальными пользователями)

- HTTPS/TLS через Nginx **либо** доступ только через VPN/корпоративную сеть (если внешний доступ не нужен).
- Автоматическое резервное копирование PostgreSQL по расписанию, независимо от состояния основного приложения (отдельный cron/systemd timer, не job внутри APScheduler).
- Резервные копии — вне основного сервера; восстановление периодически проверяется на практике.
- Логи backend — через Docker logging с ротацией и централизованным хранением.
- Healthcheck сервисов **плюс** внешний мониторинг с оповещением (healthcheck сам по себе никого не уведомляет).
- Секреты вне Git.
- PostgreSQL закрыт извне; наружу — только необходимые порты.
- Изолированные тестовое и production-окружения: отдельные БД, секреты, хранилища.

| Этап | Содержание |

| 1 | Каркас: FastAPI, PostgreSQL, SQLAlchemy, Alembic, Docker Compose, конфигурация окружений |
| 2 | Авторизация и пользователи: JWT, роли, подразделения (дерево), базовые проверки доступа |
| 3 | CRUD задач: статусы, исполнитель/ответственный/постановщик, комментарии, `task_events` |

| 8 | Тестирование и production: тесты API/бизнес-логики, HTTPS, бэкапы, мониторинг, развёртывание test → prod |

## 16. Критерии готовности MVP

- Регистрация и вход работают.
- Роли и права проверяются backend.
- Создание/изменение задач с раздельными постановщиком, исполнителем, ответственным.
- Делегирование и подзадачи работают, циклы невозможны.
- Смена ответственного — отдельное действие с записью в историю.
- Kanban отображает актуальные данные, обновляется после действий пользователя.
- Дедлайны обрабатываются планировщиком, просрочки корректно определяются.
- Рейтинг рассчитывается по базовым показателям (раздел 8).
- Уведомления не дублируются при повторных запусках планировщика.
- Ошибки API — в едином формате.
- Приложение разворачивается через Docker Compose, конфигурация окружений разделена.
- Настроены резервное копирование и базовые production-механизмы безопасности.

---

**Итоговое решение:** FastAPI (модульный монолит) + PostgreSQL + SQLAlchemy + Alembic + Docker Compose + Nginx + отдельный контейнер APScheduler. Рейтинг считается в PostgreSQL по истории событий. ClickHouse, Redis/Celery, WebSocket, MinIO — подключаются по мере реальной потребности, не заранее.
